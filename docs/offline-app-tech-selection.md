## 1. 结论摘要

| 项 | 结论 |
| --- | --- |
| 推荐路线 | **Capacitor + 原生 SQLite（@capacitor-community/sqlite）+ 将现有业务规则移植到 JS + 复用 Vue 前端 UI** |
| 备选路线 | PWA + IndexedDB（仅适合开发测试，生产环境存在存储配额与淘汰风险） |
| 核心约束 | 手机端无法运行 Python/FastAPI，必须将所有业务校验与查询逻辑移植到 JS；UI 组件与视图可高比例复用 |
| 能力覆盖 | L0（离线界面）+ L1（离线查看）+ L2（离线新增/编辑/删除/分类管理）完整，均不需要联网 |
| 多设备同步 | 本期不做，后续独立立项 |
| 对 Web 版本影响 | 不改变 Web 运行方式与业务规则，手机端仅新增本地数据层与 native 构建配置 |
| 最高风险 | 业务规则移植一致性验证，需匹配现有 59 条用例确保无行为漂移 |

| 项 | 现状 | 可复用度 |

| 生产构建 | `vite build` 已通过，产物静态文件 | Capacitor 直接使用 `vite build` 产物 |
| 当前离线能力 | 无 Service Worker、无 manifest、无本地持久化 | 从零新增 |

### 2.2 后端（Python 版）

| 项 | 现状 | 手机端适配方式 |
| --- | --- | --- |
| 框架 | Python + FastAPI + Uvicorn + SQLAlchemy | 手机端不能以本地进程运行，必须将所有业务逻辑移植到 JS |
| 数据模型 | 两张表（`categories`、`transactions`），SQLite 存储，整数分存储金额，外键 `ON DELETE RESTRICT` | 数据模型保持不变，迁移到手机端原生 SQLite |
| 业务逻辑 | 所有校验（金额、日期、分类一致性）、月份区间、占比计算均为纯函数，不依赖 HTTP 和数据库连接 | 纯函数可直接移植到 JS；带数据库查询的服务层逻辑需要调整为 JS 数据访问方法 |
| 错误码 | 1001–1010、1999 与标准文案已定义 | 错误码与文案直接复用，抛出 JS 异常替代 Python AppError |
| 预置分类 | 13 条种子数据幂等初始化 | 直接复用预置数据列表 |
| 数据库路径 | 当前固定为 `backend/ledger.db` | 手机端存储在 App 私有目录 |

### 2.3 数据约束（必须保持一致）

以下约束必须 1:1 复现在手机端，否则会产生行为漂移：

| 约束 | 说明 |
| --- | --- |
| 金额 | 单笔 `> 0`，`≤ 99,999,999.99` 元，最多 2 位小数；存储为整数分；接口输出以元保留 2 位小数 |
| 日期 | 严格 `YYYY-MM-DD`（补零）；≥ `2000-01-01`；≤ 业务时区（Asia/Shanghai）「今天」 |
| 月份 | 严格 `YYYY-MM`（月份 `01–12`）；区间为 `[当月首日, 次月首日)`，跨年月进位正确 |
| 备注 | 可为空；≤ 100 Unicode 码点 |
| 分类名称 | 去首尾空格后长度 1–20 Unicode 码点；同类型下唯一 |
| 类型 | 分类与账单类型必须一致；仅 `income` / `expense` |
| 分类删除 | 存在账单引用时拒绝删除；文案「该分类下存在记录，无法删除」；错误码 `1010` |
| 排序 | 账单按 `date DESC, id DESC`；分类按 `type` 升序、`id` 升序；报表分类按金额降序 |
| 占比 | 后端（现在手机端本地）唯一计算百分比，保留 2 位小数；允许 ±0.01% 四舍五入误差 |
| 空状态 | 筛选矛盾返回 `[]`；空月份不报错，返回 `0` 与空数组；余额允许为负 |

> 依据：`core/validators.py`、`core/money.py`、`core/timeutil.py`、`services/`、`models/`。所有约束均已枚举并可精确移植。

## 4. 为什么手机端不能沿用 PC 本地后端

这是本次方案与 PC 桌面方案的根本差别，必须先行说明：

| 原因 | 说明 |
| --- | --- |
| 没有 Python 运行时 | Android / iOS 系统不提供 Python 解释器，用户也无法自行安装 |
| 无法常驻本地服务 | 手机 App 不允许长期后台运行 HTTP 服务；iOS 对后台进程限制更严，进程随时可能被系统回收 |
| 无法打包 FastAPI | 把 Python + uvicorn 打包进 App，Android 侧技术路线受限且体积大，iOS 侧缺少可行方案；服务起来后仍受后台限制 |
| 数据位置不同 | PC 版数据库在项目目录 `backend/ledger.db`；手机端每个 App 只能写自己的沙盒目录 |
| 前端请求方式不同 | PC 版通过 HTTP 访问 `127.0.0.1:8000`；手机端没有该端口可访问 |

因此手机端必须把**数据存储下沉到手机本地**、把**业务规则从 Python 移植到 JS**，而不是复制一个「本地后端进程」。本文后续方案均基于这一前提。

## 5. 候选方案（手机端专属）

### 方案 A：PWA + IndexedDB（开发简单，体验受限）

- 形态：在现有 Vue 前端基础上增加 manifest、Service Worker 缓存外壳，新增 IndexedDB 层承载所有读写，替换原 axios 后端请求。
- 优点：
  - 开发工作量相对小；
  - 可直接在浏览器调试；
  - 用户可「添加到桌面」获得类 App 体验；
  - 不需要额外安装 native 工具链。
- 缺点：
  - **iOS 存储策略不可控**：Safari 对网站数据的配额由系统动态管理，长期不使用或存储紧张时可能被清理；Android Chrome 同样可能在系统空间不足时清理站点数据，无法像本地数据库那样保证长期持久；
  - 不是原生安装：需用户手动「添加到主屏幕」，未添加前只是普通网页，安装入口和桌面图标都不如原生 App 直观；
  - IndexedDB 不提供原生 SQLite 的约束与事务语义，外键检查、唯一性约束、写操作事务都需自行实现；
  - 虽然可用 SQLite WASM + OPFS 提升查询能力，但仍受浏览器存储清理策略约束。
- 适用场景：开发阶段快速验证，不适用于生产交付给用户。

### 方案 B：Capacitor + 原生 SQLite（推荐）

- 形态：`@capacitor-community/sqlite` 插件调用系统原生 SQLite（Android 使用系统 SQLite，可选 SQLCipher 加密；iOS 使用系统 `sqlite3`）；所有业务逻辑移植到 JS，UI 复用现有 Vue 组件；构建后打包为 `.apk` / `.ipa`。
- 优点：
  - 存储稳定：原生 SQLite 无配额限制，数据持久保存在 App 私有目录，不会被系统淘汰；
  - 原生安装：可在 Google Play / App Store 发布，或侧载安装；获得真正的手机 App 体验；
  - 视图与组件逻辑复用，仅替换数据访问层，并补充移动端样式适配；
  - Capacitor 社区生态成熟，插件稳定；
  - 数据可以导出备份（可选功能）。
- 缺点：
  - 需要移植所有业务逻辑到 JS（但本项目规模小，可完整枚举，工作量可控）；
  - 构建需要 Android Studio / Xcode 环境；
  - iOS 发布需要 Apple 开发者账号。

### 方案 C：纯原生 App 重写

- 形态：用 Jetpack Compose / SwiftUI 重写 UI 与逻辑，数据库用原生 SQLite。
- 优点：性能与体验最好。
- 缺点：
  - 完全重写所有业务、UI、校验，工作量翻倍，代码分叉，维护成本高；
  - 与当前技术栈（Vue 3 + JS）不一致，当前团队可能不熟悉原生开发；
  - 违反「保持现有 Web 版本，手机端作为子任务」的要求。
- 定位：不推荐，仅作选项列出。

### 方案 D：Flutter / React Native 跨平台重写

- 形态：用 Flutter / RN 重写整个 App，包括 UI 与业务逻辑。
- 问题：与方案 C 类似，工作量大，分叉维护；与当前 Vue 3 技术栈不兼容，需要从零开始。
- 定位：不推荐。

## 6. 方案对比

| 维度 | 权重 | 方案 A PWA+IndexedDB | 方案 B Capacitor+原生SQLite | 方案 C 纯原生重写 | 方案 D 跨平台重写 |
| --- | --- | --- | --- | --- | --- |
| 满足离线读写持久化 | 25% | 3 | 5 | 5 | 5 |
| 复用现有 Vue 前端与 UI | 20% | 5 | 5 | 1 | 2 |
| 开发与维护成本 | 15% | 5 | 4 | 1 | 2 |
| 安装与用户体验 | 15% | 2 | 5 | 5 | 5 |
| 数据可靠性（存储） | 10% | 2 | 5 | 5 | 5 |
| 对现有 Web 版本影响 | 10% | 5 | 5 | 1 | 2 |
| 工作范围符合要求 | 5% | 5 | 5 | 1 | 2 |
| **加权得分** | 100% | **3.75** | **4.85** | **3.00** | **3.50** |

> 结论：**方案 B（Capacitor + 原生 SQLite）**得分最高，是唯一同时满足「可安装 App」「数据持久」「高复用度」「低维护成本」的方案。方案 A 得分第二，仅适合作为开发预览用，不适合生产交付。

## 7. 目标架构设计（手机端）

### 7.1 整体结构

```
┌─────────────────────────────────────┐
│      Capacitor 外壳（Android/iOS）    │
│  ┌─────────────────────────────────┐  │
│  │  WebView：现有 Vue 3 构建产物     │  │
│  │  页面/组件/路由复用，数据层替换    │  │
│  └───────────────┬─────────────────┘  │
│                  │ JS 调用             │
│  ┌───────────────▼─────────────────┐  │
│  │   新增：local 数据层（JS 模块）    │  │
│  │  - core: 校验/金额转换/时区/错误码  │  │
│  │  - services: 分类/账单/报表业务逻辑 │  │
│  │  - dao: SQL 查询/CRUD 封装          │  │
│  └───────────────┬─────────────────┘  │
│                  │ SQL                │
│  ┌───────────────▼─────────────────┐  │
│  │ @capacitor-community/sqlite 插件  │  │
│  └───────────────┬─────────────────┘  │
│                  │ 绑定               │
│  ┌───────────────▼─────────────────┐  │
│  │ 手机端原生 SQLite 数据库          │  │
│  │ 数据模型与 PC 版完全一致          │  │
│  │ 预置分类 13 条，幂等初始化       │  │
│  └─────────────────────────────────┘  │
└─────────────────────────────────────┘
```

### 7.2 模块职责

| 原模块（Web） | 手机端变化 |
| --- | --- |
| `frontend/src/views/` | 完全复用，不改动数据请求调用方式 |
| `frontend/src/components/` | 完全复用 |
| `frontend/src/router/` | 完全复用 |
| `frontend/src/api/` | 保留接口定义，实现替换为 local 数据层 |
| `frontend/src/utils/` | 复用部分（格式化），新增业务工具函数 |
| `backend/app/core/` | 纯函数移植到 `frontend/src/offline/core/` |
| `backend/app/services/` | 业务逻辑移植到 `frontend/src/offline/services/` |
| `backend/app/models/` | 仅保留数据结构定义，DAO 封装在 `frontend/src/offline/dao/` |

### 7.3 关键设计要点

1. **数据模型复用**：`categories`/`transactions` 表结构与约束（主键、外键、唯一约束、CHECK）1:1 对应到 SQLite，确保约束一致性。

2. **预置分类**：13 条分类数据从 `backend/app/database/init_db.py` 直接复制到手机端初始化代码，幂等写入（仅空表时写入）。

3. **时区与日期**：业务时区仍为 `Asia/Shanghai`，JS `Intl.DateTimeFormat` 支持，可复用逻辑。

4. **金额精度**：数据库与内存中统一用**整数分**（Number 即可，单笔上限 9,999,999,999 分在 JS 安全整数范围内，无需 BigInt）；元/分换算与占比计算使用 `decimal.js` 的十进制运算并采用 `ROUND_HALF_UP`，与 Python `Decimal` 对齐。

5. **错误码与文案**：错误码与标准文案直接复用 `core/errors.py` 的定义，抛出 JS 错误对象，前端展示文案方式与 Web 版一致。

6. **排序规则**：保持与后端一致：账单 `date DESC, id DESC`；分类 `type` 升序、`id` 升序；报表分类 `amount DESC`。

7. **事务与一致性**：利用原生 SQLite 事务，所有写操作（新增、编辑、删除）均在事务内执行，失败回滚。

8. **外部依赖**：仅新增 `decimal.js`（体积小，用于金额与占比的十进制运算）；Capacitor 运行时与 SQLite 插件由框架提供。不引入状态管理库或 UI 框架。

9. **与 Web 版对比**：
   - 业务校验规则一致；
   - 数据存储结构一致；
   - 错误码与文案一致；
   - API 契约接口层一致（但走本地调用，不走 HTTP）；
   - 输出结构与排序一致（不涉及分页，现有接口无分页）；
   - 前端 UI 与交互完全一致。

## 9. 关键风险与应对

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R-01 | JS 移植后业务行为漂移（与 Python 结果不一致） | 金额精度、日期区间、占比计算不一致 | 将现有 59 条用例改写为等价 JS 用例，逐条断言错误码、文案与输出值，与 Python 版比对 |
| R-02 | Decimal 计算精度问题 | 金额四舍五入结果与 Python 不一致 | 使用 `decimal.js` 保证精度，其结果与 Python `decimal.Decimal` 可对齐 |
| R-03 | iOS 构建与安装门槛 | 无 macOS/Xcode 时无法构建 iOS 版本 | 本期可先只交付 Android；iOS 待具备 macOS 环境后追加，不影响 Android 与 Web |
| R-04 | Android 打包需要 Android Studio/JDK | 需新增数 GB 级开发环境 | 仅一次安装；也可用 CI 构建 APK |
| R-05 | 数据库版本迁移 | 后续修改表结构需要迁移 | 可在初始化时检测用户数据版本，执行迁移 SQL；插件支持迁移 |
| R-06 | IndexedDB 方案的存储风险 | iOS Safari 可能淘汰数据 | 仅用于开发预览，生产交付使用 Capacitor+原生 SQLite |
| R-07 | 原有 Web 版被破坏 | 开发过程误改主项目代码 | 所有修改限定在新增 `offline/` 目录，仅在 `api/` 目录替换实现，不修改视图与组件 |
| R-08 | Element Plus 桌面布局在窄屏下不适配 | 表格溢出、弹窗过大、按钮难以点按 | 仅新增移动端断点样式与容器宽度规则，不重写组件；验收包含窄屏可用性 |
| R-09 | JS 与 Python 的字符串长度口径差异 | 备注/分类名按码点计数不一致（emoji 等） | 使用 `Array.from(str).length` 按码点计数，与 Python `len()` 对齐，并纳入一致性用例 |

## 10. Android / iOS 差异要点

| 点 | Android | iOS |
| --- | --- | --- |
| 构建工具 | Android Studio + Gradle（JDK） | Xcode（仅 macOS 可用） |
| 安装包发布 | 可直接侧载 APK；上架 Google Play 需开发者账号与审核 | 真机安装需 Apple 开发者签名（免费个人签名有效期 7 天，付费账号 1 年）；上架 App Store 需付费开发者账号与审核 |
| 本地构建环境 | Windows/macOS 均可 | 必须 macOS；当前开发机为 Windows，**无法本地构建 iOS** |
| SQLite 版本 | 随系统更新，通常 ≥ 3.31.0 | iOS 原生，版本足够 |
| 存储位置 | App 私有目录，用户不可直接访问（可提供导出功能） | 与 Android 一致 |
| 对现有 Web 的影响 | 无 | 无 |

## 11. 验收标准（手机端离线 App）

| 编号 | 验收项 | 判定标准 |
| --- | --- | --- |

| OA-04 | 断网编辑账单 | 断网下修改记录，保存后结果正确，重启后数据保留 |
| OA-05 | 断网删除账单 | 断网下删除记录，删除后列表更新 |
| OA-06 | 断网新增分类 | 断网下新增分类成功，重名提示「该分类已存在」，新增后记账可选择 |
| OA-07 | 断网删除分类 | 无引用可删除；有引用提示「该分类下存在记录，无法删除」 |
| OA-08 | 业务规则一致性 | 金额、日期、月份、分类、百分比计算与 Web 版结果一致；错误码与文案一致 |
| OA-09 | 数据持久化 | 关闭 App 再打开，数据未丢失；系统重启后数据保留 |
| OA-10 | Web 版本不受影响 | Web 开发与启动方式、代码可运行、59 条用例结果与之前一致 |
| OA-11 | 范围约束 | 未新增登录、多用户、云同步、支付、导入导出等功能 |
| OA-12 | 一致性测试 | 改写后的等价 JS 用例全部通过，错误码、文案与计算值均与 Python 版一致 |

## 12. 明确不在本子任务范围

| 项 | 说明 |
| --- | --- |
| 多设备同步 / 云同步 | 需要服务器、账号、幂等键与冲突合并，独立立项 |

| 后端重写（Web 版） | 不改变 Web 版业务与代码 |
| 线上部署 | 不在本子任务内，仍为主项目待办 |
| 数据导出 / 备份 | 可选功能，默认不做；若用户要求可追加 |
