## 0. 审查方法

1. 以 `spec.md` 为**最高优先级基线**，architecture / database-design / api-design 逐层向下核对。
2. 对每项功能做"spec → API → 数据库 → 前端消费"四段式追踪，任一段断裂即记为问题。
3. 对可验证性做**数值级复核**（用 database-design 的测试数据反算 api-design 的示例值）。
4. 对错误处理与边界，逐条比对 spec E-01 ~ E-16 与 API 错误码。

## 2. API → 数据库可实现性

| API 能力 | 数据库支撑（database-design） | 可实现 |
| --- | --- | --- |
| 账单按月筛选 + `date DESC, id DESC` | `date` TEXT（字典序=时间序）+ `ix_transactions_date` | ✅ |
| 账单增/改/删 | `transactions` CHECK + FK | ✅ |
| 元↔分转换 | `amount INTEGER` + 应用层 `core/money.py` | ✅ |
| 分类按 type 筛选/分组 | `categories` + `ux_categories_name_type` | ✅ |
| 分类重名（1009） | 唯一索引 `(name,type)` | ✅ |
| 删除被引用分类被拒（1010） | `ON DELETE RESTRICT` + 应用层引用计数 | ✅ |
| 收入/支出/结余 | `SUM(amount)`（整数分）+ 应用层减法 | ✅ |

| 跨年月份区间（AC-17） | `date >= '2026-12-01' AND date < '2027-01-01'` | ✅ |

| 日期 ≤ 业务时区今天（1004） | **应用层**（"今天"动态） | ✅ |

**结论：8 个端点的每一项能力均可由现有表结构 + 索引 + 应用层校验实现，无需新增表或字段。**

## 3. 前端是否能消费所有 API

| spec §6.4 页面 | 使用的 API | 可消费 |
| --- | --- | --- |
| 记录列表 `/` | `GET /transactions`（+ `GET /categories` 映射分类名） | ✅（需一次映射，见 C-04） |
| 新增/编辑弹窗 | `POST` / `PUT /transactions`、`GET /categories?type=` | ✅ |
| 分类管理 `/categories` | `GET` / `POST` / `DELETE /categories` | ⚠️ 见 R-04 |
| 月度报表 `/reports` | `GET /reports/monthly` | ✅ |

**全部 8 个端点均有前端消费者，无"孤儿接口"。**

前端消费缺口：
- **R-04**：spec §7.5 要求删除被引用分类时提示"该分类下存在 **N** 条记录"，但 api-design 裁决（C-03）不返回条数 → 前端**无法生成含条数的提示**，只能降级为通用文案。需求与契约不一致。
- **C-04**：账单列表项不含 `category_name`，前端必须用 `GET /categories` 做 id→name 映射。可行，但增加一处耦合；若分类列表未缓存，可能出现"分类名短暂缺失"。

## 4. 字段名与类型一致性

| 字段 | spec | database | api | 一致 |
| --- | --- | --- | --- | --- |
| `amount` | 元（接口） | 分（库） | 元 number | ⚠️ 同名不同单位，见 R-17 |
| `type` | income/expense | income/expense | income/expense | ✅ |
| `category_id` | ✓ | ✓ | ✓ | ✅ |
| `date` | `YYYY-MM-DD` | TEXT+CHECK | string `YYYY-MM-DD` | ✅ |
| `note` | ≤100 | TEXT+CHECK | string\|null | ✅ |
| `name` | 1–20 | TEXT+CHECK | string | ✅ |
| `total_income` / `total_expense` | §6.3 定义 | — | 同名 | ✅（已按 spec 裁决 C-01） |
| `balance` | §6.3 | — | number（可负） | ✅ |
| `expense_by_category` | §6.3 | — | 同名 | ✅ |
| `category_name` | §6.3 | JOIN 得到 | 同名 | ✅ |
| `percentage` | 2 位小数 | 后端计算 | number | ✅ |

**发现的问题：**
- **R-01（高）**：api-design §2.3 把 `Money` 定义为 `> 0 且 ≤ 99999999.99`，但把该类型复用于 `total_income` / `total_expense`：
  - 空月份时两者为 `0.00`，违反 `> 0`；
  - 汇总额可超过单笔上限 `99,999,999.99`，违反上限约束；
  - 而 `balance` 又因可为负被写成 `number`，导致同一响应内金额类型标注不统一。
  → 类型定义与聚合语义冲突，需裁决。
- **R-17（低）**：`amount` 在库为「分」、在 API 为「元」，同名不同单位，跨层阅读易误判，建议在文档字段说明中强制标注单位。

## 6. 月度统计是否可验证

**数值级复核（用 database-design §9.2 测试数据反算 api-design §3.8 示例）：**

| 项 | database-design 测试数据 | 计算结果 | api-design 示例 | 一致 |
| --- | --- | --- | --- | --- |
| 2026-10 收入 | 1200000 + 50000 分 | 1250000 分 = **12500.00** | `12500.00` | ✅ |
| 2026-10 支出 | 3333+1250+300000+210000 分 | 514583 分 = **5145.83** | `5145.83` | ✅ |
| 2026-10 结余 | 1250000 − 514583 | 735417 分 = **7354.17** | `7354.17` | ✅ |
| 居住占比 | 300000 / 514583 | **58.30%** | `58.30` | ✅ |
| 购物占比 | 210000 / 514583 | **40.81%** | `40.81` | ✅ |
| 餐饮占比 | 3333 / 514583 | **0.65%** | `0.65` | ✅ |
| 交通占比 | 1250 / 514583 | **0.24%** | `0.24` | ✅ |
| 占比合计 | — | **100.00%**（落在 99.99–100.01 容差内） | — | ✅ |
| 跨年 2025-12 | 5000 分 | **50.00 / 结余 −50.00** | 未在 API 示例中出现 | ⚠️ R-07 |

**结论：核心月度统计（当月汇总、占比、排序、精度）可在数值层面完全验证，四文档互相印证。**

**问题：**
- **R-07（中）**：api-design 未提供**跨年月份**的 JSON 示例，AC-17（跨年）只能靠 database-design 的 SQL 验证，缺少 API 级断言样例。
- **R-08（中）**：报表/列表 `month` 缺省 = 业务时区"当前月"，结果随运行日期变化，api-design 未说明测试中如何固定，易导致用例不可复现。建议测试一律显式传 `month`。
- **R-12（低）**：spec §6.2 成功示例为**单个对象**，而列表接口返回**数组**，属合理推断但未在 spec 明示。

## 7. 错误处理与边界条件覆盖

**spec E-01 ~ E-16 覆盖矩阵**

| spec | 场景 | API 错误码 | 覆盖 |
| --- | --- | --- | --- |
| E-01 | 金额非法（空/非数字/≤0/超 2 位小数） | 1002 | ✅ |
| E-02 | 金额超上限 | 1003 | ✅ |
| E-03 | 必填缺失/格式不符 Pydantic | 1001（422→400） | ✅ |
| E-04 | 类型与分类不一致 | 1006 | ✅ |
| E-05 | 引用不存在分类 | 1007 | ✅ |
| E-06 | 日期非法 | 1004 | ✅ |
| E-07 | 月份非法 | 1005 | ✅ |
| E-08 | 备注超长 | 1001 | ⚠️ 文案不一致，见 R-02 |
| E-09 | 分类重名 | 1009 | ✅ |
| E-10 | 分类名非法 | 1001 | ⚠️ 文案不一致，见 R-02 |
| E-11 | 删除被引用分类 | 1010 | ✅ |
| E-12 | 记录不存在 | 1008 | ✅ |
| E-13 | 无数据 | 200（0 值 + 空数组） | ✅ |
| E-14 | 服务端异常 | 1999 | ✅ |
| E-15 | 前端网络错误 | 前端拦截器（非后端响应） | ✅ |
| E-16 | 重复提交 | 前端禁用按钮 | ✅ |

**覆盖完整（16/16），无遗漏错误场景。**

**边界问题：**
- **R-02（高）**：spec §9 对错误码 1001 下的场景给出了**细分文案**（E-08"备注长度超限"、E-10"分类名称不合法"），而 api-design §2.2 将 1001 统一为"参数不合法" → 用户可见文案被降级，验收时无法按 spec §9 逐条断言。
- **R-09（中）**：spec 未定义"删除**不存在的分类**"的错误码归属；api-design 采用 1007（分类不存在）。合理，但属契约孤儿，需在 spec 补条款或在 API 文档显式声明。
- **R-13（低）**：`{id}` 传入非整数（如 `/api/transactions/abc`）返回 1001 还是 1008，未明确。
- **R-06（中）**：spec §5.1 表述"按码点计数，emoji 计 1"自相矛盾（组合 emoji 含多码点）；实现侧 Python `len()` 与 SQLite `length()` **均按码点**，二者一致，但 spec 表述需修正为"按 Unicode 码点计数"。
- **R-14（低）**：`GET /transactions` 用不存在的 `category_id` 筛选返回空数组（api-design §3.1 明确不校验存在性）。这是有意决策，但未回写 spec，建议显式声明。
- **R-15（低）**：报表两种空态（"本月暂无数据" / "本月暂无支出数据"）由前端依据 `total_income/total_expense` 判定，api-design 未给出判定公式，建议补充。
- **R-10（中）**：`TransactionOut` 不含 `created_at` / `updated_at`，spec §7.2 要求的"刷新 `updated_at`"无法通过 API 观测，只能查库验证。

## 10. 放行建议

**结论：有条件放行 —— 不阻断进入 Coding，但需先裁决 R-01、R-02。**

| 处置 | 项 |
| --- | --- |
| **Coding 前必须裁决** | R-01（金额类型拆分）、R-02（错误文案回退到 spec §9） |
| 可与 Coding 并行处理 | R-03、R-05、R-06、R-07、R-08、R-09、R-10 |
| 建议顺手修正 | R-04（需同步 spec）、R-11 ~ R-17 |

**不改代码即可落地的两个动作**
1. 修订 `docs/api-design.md`：拆分 `Money` / `AggregateAmount` / `SignedAmount`；把 1001 文案标注为"以 spec §9 细分文案为准"；补跨年示例与空态判定公式。
2. 在 `spec.md` 补 3 条：删除不存在分类的错误码、矛盾筛选参数的行为、列表响应为数组。

**结论性判断**：四份文档在**功能、数据模型、金额与月份口径、错误码**四个主干上高度自洽，未发现设计层不可实现的矛盾；所有问题均为契约表述与类型标注层面的可修补项，**具备进入 Coding 阶段的条件**。
